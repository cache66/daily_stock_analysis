# 外部系统能力地图：面向本地策略框架的借力与避坑

最后更新：2026-04-27

## 1. 这份文档解决什么问题

这份文档不是“开源项目排行榜”，而是站在当前本地策略框架视角，回答下面几个问题：

1. 外部哪些开源系统在某一层明显比我们强。
2. 它们强的到底是数据、基本面、短线理解、新闻、agent、回测，还是工程结构。
3. 我们应该直接接入什么，参考实现什么，哪些只值得观察，哪些值得把源码拉下来深挖。
4. 如何避免“自己重复造轮子”，同时避免“为了追热点把现有 4 条主策略打散”。

当前判断原则：

- 我们不追求整体替换现有框架。
- 优先考虑“局部借力”，把外部系统当作能力提供方，而不是上层决策真源。
- 主策略仍保持收敛到 4 条：
  - `trend_leader_unified`
  - `earnings_surprise`
  - `hundred_day_high`
  - `monthly_slow_rise`

## 2. 我们当前框架的边界

当前本地框架的优势不在“通用量化底座最强”，而在“面向 A 股主策略的可落地闭环”：

- 有明确的 4 条主策略分层，而不是无穷扩策略名。
- 有每日快照、结果回看、策略文档、性能优化、运行入口。
- `trend_leader_unified / earnings_surprise / hundred_day_high / monthly_slow_rise` 都已经开始形成可解释字段和默认口径。

当前明显不如成熟外部系统的层主要有：

- 数据接入层：多源统一、数据标准化、缓存体系、下载速度。
- 研究层：因子库、统一排序器、自动实验、模型/因子迭代。
- 回测评估层：标准化成本口径、组合层、执行层、样本外对照。
- 新闻与 agent 层：多角色分析、结构化辩论、用户交互产品化。

因此，正确方向不是“换掉我们的系统”，而是“按层借力”。

## 3. 外部能力分层地图

### 3.1 数据获取与缓存

这一层重点看：

- 数据覆盖面
- 下载速度
- 多源统一接口
- 缓存/更新/复用能力

值得优先关注的系统：

- `OpenBB`
  - 强项：统一金融数据平台，多入口消费（Python / API / MCP / Workspace）。
  - 适合我们借的层：上游数据下载与标准化，不适合直接代替策略引擎。
- `QUANTAXIS`
  - 强项：A 股本地化数据底座、任务化、账户体系。
  - 适合我们借的层：A 股场景下的数据组织和本地数据仓思路。
- `vn.py`
  - 强项：生态成熟，研究与交易连接更顺。
  - 适合我们借的层：数据与交易入口之间的工程边界设计。

对我们的可执行启发：

- 可把 `OpenBB` 作为候选上游下载器，用于：
  - 行情数据
  - 基本面数据
  - 新闻/事件目录
- 但落到本地策略时，仍要统一映射到我们自己的字段契约，不直接让上游项目决定策略字段。

### 3.2 基本面初筛与财务研究

这一层重点看：

- 财报字段覆盖
- 质量因子
- 多季度连续性
- 训练/排序能力

值得优先关注的系统：

- `Qlib`
  - 强项：因子工程、Alpha 特征库、横截面研究、ML 排序框架。
  - 对我们最值钱的是“统一研究层”，不是现成 A 股短线答案。
- `RD-Agent`
  - 强项：自动做 quant R&D，包含研究、开发、反馈闭环。
  - 对我们最值钱的是自动找因子、自动试验、自动筛排序方案。
- `RQAlpha`
  - 强项：回测与研究口径更标准。
  - 对我们最值钱的是验证财务因子是否真有效，而不是只看规则叙述。

对我们的可执行启发：

- `earnings_surprise` 最适合先吃这层能力：
  - 多季度 `surprise history`
  - 财务质量连续性
  - 统一的基本面排序器
- `monthly_slow_rise` 也应该吃这层：
  - ROE / 毛利 / 现金流 / 利润率连续性
  - 不是只看图形

### 3.3 短线选股、形态、筹码、博弈理解

这一层重点看：

- A 股短线语境是否真实
- 是否理解龙头、辨识度、筹码、游资、大单异动
- 是否能给出可解释信号，而不是只给黑盒打分

值得优先关注的系统：

- `myhhub/stock`
  - 强项：平台突破、高而窄旗形、海龟、低 ATR 成长、筹码分布、验证链路。
  - 对我们最有直接策略参考价值。
- `FinGenius`
  - 强项：A 股短线 agent 语境，强调游资、筹码、大单异动、博弈。
  - 对我们最有直接“短线视角补充”价值。
- `TradingAgents-CN`
  - 强项：中文金融分析产品壳、多模块组织、批量分析与报告。
  - 对我们更偏产品层和分析组织层。

对我们的可执行启发：

- `trend_leader_unified`
  - 可借 `myhhub/stock` 的突破平台、高旗形、低 ATR 成长、筹码分布思路。
  - 可借 `FinGenius` 的游资/大单异动/博弈视角，作为增强因子或解释因子，而不是主判定真源。
- `hundred_day_high`
  - 与 `myhhub/stock` 的平台突破/海龟/高旗形最接近。
  - 可以补“突破前压缩 + 突破后跟随质量 + 筹码结构”。

### 3.4 新闻、事件、情绪

这一层重点看：

- 新闻源覆盖
- 事件抽取
- 情绪分类
- 对短线策略是否有可用增强，而不是噪声放大

值得优先关注的系统：

- `TradingAgents / TradingAgents-CN`
  - 强项：把新闻、情绪、观点整合成多角色分析流程。
- `FinGenius`
  - 强项：更贴 A 股短线用户语境的舆情与博弈描述。
- `OpenBB`
  - 强项：可作为上游新闻/事件数据抓取底座。

对我们的可执行启发：

- `earnings_surprise`
  - 可以让新闻层先做“事件目录 + 初筛”，再回到我们自己的财务规则。
- `trend_leader_unified`
  - 新闻更适合作为二阶段增强，而不是主扫描必依赖项。
- 当前最忌讳的是把新闻因子直接抬成主判定，否则容易把噪声当 alpha。

### 3.5 多智能体分析与报告

这一层重点看：

- 是否适合做用户侧解释
- 是否能做冲突观点整合
- 是否比当前固定模板更有信息量

值得优先关注的系统：

- `TradingAgents`
  - 强项：角色明确，研究团队式分析流程清晰。
- `TradingAgents-CN`
  - 强项：中文用户产品化、分析任务编排、配置层完整。
- `FinGenius`
  - 强项：A 股短线博弈语言自然。
- `ai-hedge-fund`
  - 强项：演示传播性强，适合借展示，不适合借核心策略逻辑。

对我们的可执行启发：

- 当前不建议把 agent 当主选股器。
- 更适合把 agent 放到：
  - 二阶段解释
  - 候选对比
  - 风险提示
  - 新闻摘要
- 也就是“先有规则/因子候选，再让 agent 解释”，而不是“先让 agent 选股”。

### 3.6 回测、绩效评估、执行口径

这一层重点看：

- 交易成本
- 滑点
- 组合层
- 交易规则口径
- 样本外验证

值得优先关注的系统：

- `RQAlpha`
  - 强项：经典回测口径与扩展性。
- `WonderTrader`
  - 强项：大规模定时选股、执行引擎、工程化更强。
- `vn.py`
  - 强项：从研究到执行更容易闭环。

对我们的可执行启发：

- 我们当前最需要补的是“标准化回测口径”，不是马上接实盘。
- `signal_snapshot` 评估链路后面可逐步补：
  - 组合层
  - 更真实的成交成本
  - 规则与组合分离

### 3.7 研究自动化与因子发现

这一层重点看：

- 自动试验
- 因子搜索
- 模型/因子共优化
- 研究闭环

值得优先关注的系统：

- `RD-Agent`
  - 这是这一层最值得重视的系统。
- `Qlib`
  - 适合配合做统一特征与实验框架。
- `vnpy.alpha`
  - 更适合把研究结果接回真实工程。

对我们的可执行启发：

- 下一阶段最值得引入的不是“更多策略名”，而是：
  - 给现有 4 条主策略加统一因子层
  - 给统一因子层加自动实验能力
  - 给自动实验加评估闭环

### 3.8 系统结构与工程底座

这一层重点看：

- 模块边界
- 插件化
- 调度
- 配置中心
- 任务组织

值得优先关注的系统：

- `OpenBB`
  - 数据接口层组织方式
- `TradingAgents-CN`
  - 产品与分析任务组织方式
- `WonderTrader`
  - 高性能选股与执行引擎分层
- `vn.py`
  - 模块生态与边界清晰度

对我们的可执行启发：

- 我们不一定要变成“大平台”，但应该逐步把：
  - 数据层
  - 策略层
  - 因子层
  - 评估层
  - agent 解释层
  分得更清楚。

## 4. 逐个项目看：它们的优点、适用层、是否值得深挖

### 4.1 OpenBB

- 适用层：数据获取与统一接口
- 优点：
  - 数据平台定位明确，当前公开核心已收敛为 `Open Data Platform`
  - `Provider / Fetcher / Router / OBBject` 这套抽象很成熟，适合做统一数据层参考
  - 同一底层能力可同时暴露给 Python / REST API / CLI / MCP / Workspace，多消费面能力非常强
- 不适合直接替代：
  - 我们的 A 股主策略与快照链路
- 建议：
  - 作为“数据候选底座”高优先级观察
  - 后续如做下载接入，先做离线实验，不直接替换现有 provider
  - 首轮正式结论：见 `docs/architecture/openbb-source-dive.md`

### 4.2 Qlib

- 适用层：因子研究、排序器、ML 研究
- 优点：
  - Alpha 特征库成熟
  - 横截面研究能力强
  - `DatasetH / handler / segments / record` 形成了统一研究底座，不只是模型列表
  - `qrun + workflow + recorder + task management` 把数据、训练、回测、记录、滚动实验放进同一套契约
- 不适合直接替代：
  - 我们现有规则型主策略入口
  - 当前本地短线信号层与每日快复盘链路
- 建议：
  - 高优先级深挖
  - 最适合服务 `earnings_surprise / monthly_slow_rise` 的质量层和统一排序层
  - 第一轮正式深挖记录：见 `docs/architecture/qlib-source-dive.md`

### 4.3 vn.py

- 适用层：工程底座、研究到执行的桥接
- 优点：
  - 工程成熟，模块边界清楚
  - 插件生态强，研究层、回测层、执行层能共存但不混写
  - `vnpy.alpha` 已把 `dataset / model / strategy / lab` 显式化，适合观察“研究结果如何接回工程系统”
- 不适合直接替代：
  - 当前本地策略逻辑本身
- 建议：
  - 中高优先级观察
  - 更适合作为“结构学习对象”
  - 首轮正式结论：见 `docs/architecture/vnpy-source-dive.md`

### 4.4 WonderTrader

- 适用层：大规模选股与执行引擎
- 优点：
  - 明确把 `SEL` 选股引擎单独抽层，特别适合看全市场扫描组织方式
  - 高性能数据组织、回测与执行衔接更强
  - Python 通过 `wtpy` 接入，说明策略表达层和性能层可以分开
- 建议：
  - 对 `trend_leader_unified / monthly_slow_rise` 的全市场扫描最有借鉴价值
  - 首轮正式结论：见 `docs/architecture/wondertrader-source-dive.md`

### 4.5 QUANTAXIS

- 适用层：A 股本地化底座、任务和数据体系
- 优点：
  - A 股场景完整，本地数据、日历、市场语义和任务化思路比较全
  - 数据、回测、账户、任务化一体
  - `QARSBridge / QADataBridge` 说明它也在正面补性能与桥接层
- 建议：
  - 中优先级参考数据与任务层
  - 首轮正式结论：见 `docs/architecture/quantaxis-source-dive.md`

### 4.6 RQAlpha

- 适用层：标准化回测与绩效口径
- 优点：
  - 回测口径标准，成本、风险、分析输出分层明确
  - `mod` 架构很适合看评估层如何拆分
  - 适合做外部基线和组合级验证参考
- 建议：
  - 高优先级参考评估层，不用拿来替代策略层
  - 首轮正式结论：见 `docs/architecture/rqalpha-source-dive.md`

### 4.7 myhhub/stock

- 适用层：A 股实战选股、形态、筹码
- 优点：
  - 与我们策略语境接近，尤其贴近 `trend_leader_unified / hundred_day_high`
  - 平台突破、海龟、高旗形、回踩年线、低 ATR 这些实现都能直接拆成形态增强字段
  - 自带 `CYQ` 筹码分布算法，可直接转成集中度、成本区、获利盘比例等摘要指标
- 建议：
  - 高优先级深挖
  - 对 `trend_leader_unified / hundred_day_high` 价值最大
  - 首轮正式结论：见 `docs/architecture/myhhub-stock-source-dive.md`

### 4.8 TradingAgents / TradingAgents-CN

- 适用层：agent 分析流程、报告组织、产品化
- 优点：
  - 多角色分析流程清晰，`TradingAgents-CN` 已把分析 -> 对辩 -> 决策 -> 风险审查显式编排成图
  - 中文产品壳成熟度较高，配置中心、文档中心、批量分析和报告导出都比较完整
- 不足：
  - 更像分析平台，不是我们当前要对标的短线主策略闭环
- 建议：
  - 中高优先级参考解释层与产品层
  - `TradingAgents-CN` 首轮正式结论：见 `docs/architecture/tradingagents-cn-source-dive.md`

### 4.9 FinGenius

- 适用层：A 股短线 agent 视角、舆情/游资/筹码/异动
- 优点：
  - 语境贴近 A 股短线用户
  - `Research -> Battle` 两阶段结构很适合做候选解释层，而不是主扫描层
  - 热钱、筹码、大单异动这些维度拆分清楚，适合给 `trend_leader_unified` 做解释增强
- 不足：
  - 工程成熟度和公开可验证绩效不如成熟量化底座
- 建议：
  - 高优先级深挖
  - 更适合作为“短线解释与增强因子来源”
  - 首轮正式结论：见 `docs/architecture/fingenius-source-dive.md`

### 4.10 RD-Agent

- 适用层：研究自动化、因子发现、实验闭环
- 优点：
  - 最可能推动我们进入“下一代研究方式”
  - 不是加更多策略，而是加更强研究能力
  - `quant` 分支不是单点脚本，而是把 hypothesis / experiment / coding / running / feedback 串成统一 loop
  - 能在 factor 与 model 两类动作之间切换，并维护 baseline / SOTA / 增量实验的统一反馈链
- 不足：
  - 不是现成产品壳
  - 不是直接替换当前信号系统
  - 强绑定 `Qlib`、Docker、Linux 和中长周期量化研究口径，不适合作为 A 股短线主引擎直接迁移
- 建议：
  - 最高优先级深挖
  - 重点看它怎么组织实验、反馈和因子迭代
  - 第一轮正式深挖记录：见 `docs/architecture/rd-agent-source-dive.md`

### 4.11 ai-hedge-fund

- 适用层：演示、agent 展示、交互包装
- 优点：
  - 传播性强
  - 多角色分析壳清楚，用户更容易理解“agent 在做什么”
  - CLI / Web / Backtester 一起存在，适合借展示与解释组织方式
- 不足：
  - 更偏研究/教育 demo
  - 不适合作为 A 股短线策略基线
- 建议：
  - 低优先级观察
  - 只借展示，不借核心策略逻辑
  - 首轮正式结论：见 `docs/architecture/ai-hedge-fund-source-dive.md`

## 5. 映射回我们当前 4 条主策略

### 5.1 `trend_leader_unified`

最值得借：

- `myhhub/stock`
  - 平台突破
  - 高而窄旗形
  - 低 ATR 成长
  - 筹码分布
- `FinGenius`
  - 游资视角
  - 大单异动
  - 短线博弈解释
- `WonderTrader`
  - 全市场高性能扫描组织方式
- `RD-Agent`
  - 后续做统一排序器实验

不建议直接借：

- 让 agent 直接给主扫描结果
- 让新闻因子变成主硬门槛

### 5.2 `earnings_surprise`

最值得借：

- `Qlib`
  - 多因子研究
  - 横截面排序
  - 质量因子组织
- `RD-Agent`
  - 多季度因子自动试验
  - 因子组合搜索
- `OpenBB`
  - 财务和事件上游下载
- `TradingAgents / FinGenius`
  - 只作为事件解释与新闻补充

关键方向：

- 先做规则初筛
- 再做统一财务质量排序
- 最后才让新闻/agent 做解释增强

### 5.3 `hundred_day_high`

最值得借：

- `myhhub/stock`
  - 平台突破
  - 海龟
  - 高旗形
  - 低 ATR 成长
- `trend template / Minervini` 路线对应的外部实现思路
- `WonderTrader`
  - 高性能扫描组织

关键方向：

- 形态 + 压缩 + 突破后跟随
- 行业强度
- 不只看“新高”本身

### 5.4 `monthly_slow_rise`

最值得借：

- `Qlib`
  - 质量层、排序层
- `RD-Agent`
  - 因子和参数自动迭代
- `myhhub/stock`

### 7.5 执行现实判断：不要把这项需求当成一次性完结文档

如果严格按上面的拆分方式，把 `RD-Agent / Qlib / myhhub/stock / FinGenius` 都做到同一深度的源码拆解，再统一回写总地图，这件事会明显偏长，不适合按“一次性全部做完”的方式推进。

原因很直接：

- 这些仓库不是同一类型项目，有的是通用研究框架，有的是量化底座，有的是 A 股实战脚本，有的是 agent 产品壳
- 单是 `RD-Agent` 一项，就已经包含 CLI、workflow、scenario、developer、feedback、log/UI 等多层结构，不是读一个入口脚本就能结束
- 如果每个仓库都要求“读源码 + 做结构图 + 提炼可借点 + 映射到我们框架”，总工作量天然会放大

所以更合理的推进方式是：

1. 先把总地图文档定成“导航文档”，不追求一次写成终稿
2. 每个重点仓库单独沉淀一份源码深挖记录
3. 每完成一个仓库，再把结论回填到总地图
4. 总地图始终保持“当前已确认结论”，而不是“预设最终全量结论”

换句话说，这项需求的完成定义不应该是：

- “把所有外部系统一次性研究完，再写一版大全文档”

而应该是：

- “先有总地图，再按仓库逐个深挖，滚动补齐结论”

建议把后续交付口径改成 3 层：

1. 总地图：只负责优先级、映射关系、阶段判断
2. 仓库深挖文档：只负责单仓库结构、能力点、可借点、不可借点
3. 集成决策文档：只负责哪些能力真的要接入我们当前 4 条主策略

这样做的好处是：

- 不会因为一个仓库读得深，就卡住整个文档任务
- 不会把“信息收集”与“接入决策”混在一起
- 后面即使中途停下来，已有结论也都是可复用的

### 7.6 执行节奏：直接分析并记录结果，不做重复确认

后续默认执行方式再收紧一层：

- 直接按既定顺序连续分析相关开源工程
- 直接产出独立深挖文档
- 直接回填总地图里“对我们有用的结论”
- 不再每完成一站就重复征求确认

默认只保留 3 类内容：

1. 这个仓库真正的优点
2. 对我们当前框架有用、能借的部分
3. 不适合直接接入、只适合参考的部分

默认不再追求的内容：

- 过多过程记录
- 逐步汇报每个阅读动作
- 每轮都单独确认是否继续

只有在下面几种情况才打断当前节奏：

- 发现仓库已明显不值得继续深挖
- 遇到高成本动作，例如需要本地完整运行、需要大量依赖安装、需要长时间联网实验
- 发现结论会直接影响我们当前主策略方向，需要你拍板

也就是说，后续的默认口径是：

- “直接分析，直接记录，直接回填，只在高风险分叉时中断”
