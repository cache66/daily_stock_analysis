# myhhub/stock 源码深挖记录
最后更新：2026-04-27

## 1. 仓库定位

`myhhub/stock` 实际上是 `InStock` 股票系统。它不是研究底座型项目，也不是多智能体分析平台，而是非常偏 A 股实战的“数据抓取 + 技术指标 + 形态识别 + 策略选股 + 验证回测”一体化系统。

对我们最重要的判断是：

- 它最有价值的不是通用量化研究能力
- 它最有价值的是贴近 A 股语境的形态实现、筹码分布实现和验证链路
- 它比 `RD-Agent / Qlib` 更接近我们当前 `trend_leader_unified / hundred_day_high` 的策略层，而不是研究层

这意味着它更像我们后续做“趋势突破 / 形态质量 / 筹码增强”时的实现参考库，而不是统一研究框架。

参考入口：

- GitHub 仓库：<https://github.com/myhhub/stock>
- 本轮查看源码基于本地临时克隆：`b6e0ca2`

## 2. 核心结构与入口

本轮优先看的真实入口包括：

- 项目总览：`README.md`
- 策略表注册：`instock/core/tablestructure.py`
- 平台突破：`instock/core/strategy/breakthrough_platform.py`
- 海龟交易：`instock/core/strategy/turtle_trade.py`
- 回踩年线：`instock/core/strategy/backtrace_ma250.py`
- 低 ATR 成长：`instock/core/strategy/low_atr.py`
- 高而窄旗形：`instock/core/strategy/high_tight_flag.py`
- 筹码分布：`instock/core/kline/cyq.py`

可以先把它理解成 4 层：

1. 日常数据层
   - 每日股票、ETF、资金流、龙虎榜、基本面等表结构和抓取结果
2. 指标与形态层
   - `talib` 指标、K 线形态识别、筹码分布
3. 策略选股层
   - 平台突破、海龟、高旗形、回踩年线、低 ATR 等
4. 验证与展示层
   - 回测验证、数据库落表、Web 展示、批量时间作业

## 3. 真正的优点

### 3.1 它的策略语言非常贴近 A 股趋势股语境

`README.md` 和策略模块都表明，这个仓库不是在做泛化“全球股票量化”叙事，而是明确围绕 A 股常见短中期强势形态：

- 平台突破
- 海龟新高
- 高而窄旗形
- 回踩年线
- 低 ATR 成长

这对我们最有价值，因为我们当前最需要补强的并不是再加一个大而全平台，而是把 `trend_leader_unified / hundred_day_high` 的形态层做得更扎实、更可解释。

### 3.2 它提供了可以直接拆解的形态实现，而不是只给概念名

这一点很关键。它不是只在 README 里写“支持平台突破”，而是把条件明确落成代码：

- `breakthrough_platform.py`
  - 用 `MA60` 作为平台轴
  - 要求存在 `open < MA60 <= close` 的上穿日
  - 上穿日还要通过 `enter.check_volume(...)` 的放量确认
  - 突破前价格相对 `MA60` 的偏离要落在 `-5% ~ +20%`
- `turtle_trade.py`
  - 直接实现“最后一个交易日收盘价 >= 最近 60 日最高收盘价”
- `backtrace_ma250.py`
  - 先要求从 `MA250` 下方向上突破
  - 后段必须始终运行在 `MA250` 之上
  - 高点后回踩低点与高点相差 `10-50` 天
  - 回踩还要伴随显著缩量
- `high_tight_flag.py`
  - 明确要求前段涨幅足够大
  - 且要出现连续两天 `>= 9.5%` 的强势拉升

这类实现虽然不算复杂，但胜在规则清楚、可拆、可迁移。

### 3.3 它不是只看图形，还把量能确认放进了形态判断

`breakthrough_platform.py` 和 `backtrace_ma250.py` 都不是纯价格形态，而是把：

- 放量突破
- 缩量回踩
- 时间窗约束

放进条件里。

这和我们当前主策略需要补的方向一致。我们现在已经有趋势和新高框架，但对“突破是不是高质量”“回踩是不是健康”这类结构确认，还可以从这里借更明确的二级过滤条件。

### 3.4 它自带筹码分布算法实现，这一点对我们非常值钱

`instock/core/kline/cyq.py` 不是简单调外部接口，而是自己实现了 `CYQCalculator`：

- 按历史 `open/close/high/low/turnover` 叠加筹码分布
- 输出 `avg_cost`
- 输出 `benefit_part`
- 输出 `90% / 70%` 筹码区间
- 输出集中度 `concentration`

这比单纯“调一个筹码接口返回 JSON”更有借鉴价值，因为：

- 算法逻辑是透明的
- 可以按我们的字段体系做裁剪
- 可以变成 `trend_leader_unified / hundred_day_high` 的筹码增强字段

### 3.5 它的数据表和策略注册方式说明它有完整验证链路

`tablestructure.py` 里能看到：

- 日行情字段
- 基本面字段
- 资金流字段
- 策略模块注册

README 也明确把“选股验证”和“批量时间作业”当成系统内能力。这说明它不是只给一些孤立脚本，而是把“扫描 -> 落表 -> 验证”串了起来。

对我们来说，最值得借的不是它整套数据库结构，而是它这种“策略要能批量验证”的工程习惯。

## 4. 我们能直接用的能力

### 4.1 给 `hundred_day_high` 补平台突破和跟随质量

这是当前最直接的接入方向。

可直接借的点：

- `MA60` 平台约束
- 放量突破确认
- 突破前相对均线偏离区间
- 海龟式新高确认

落到我们框架里，可以形成：

- 新高不是只看 `close >= rolling_high`
- 而是“新高 + 平台结构 + 放量确认”
- 再补一层突破后 `3-5` 日跟随质量

### 4.2 给 `trend_leader_unified` 补强趋势结构和回踩质量

`backtrace_ma250.py` 对我们很有价值，因为它实际上已经在表达一种“Stage-2 趋势后的健康回踩”：

- 长期均线向上突破
- 均线之上运行
- 回踩不破关键趋势
- 回踩伴随缩量

这特别适合迁移成 `trend_leader_unified` 的：

- `pullback_quality`
- `stage2_confirmation`
- `volume_dry_up_on_pullback`

而不是只用当前较粗粒度的 breakout / pullback 标签。

### 4.3 给 `trend_leader_unified / hundred_day_high` 增加筹码结构字段

`CYQCalculator` 最值得迁移的不是整张分布图，而是几类摘要字段：

- 平均成本
- 获利盘比例
- 70% / 90% 成本区间
- 集中度

这些字段非常适合落成我们自己的：

- `chip_avg_cost`
- `chip_benefit_part`
- `chip_concentration_70`
- `chip_concentration_90`
- `price_vs_chip_cost`

然后用于：

- 突破前是否筹码集中
- 突破时是否大部分筹码已处于获利状态
- 回踩时是否仍在主成本区之上

### 4.4 给 `monthly_slow_rise` 借“低 ATR / 稳定趋势”视角，但不能照搬

`low_atr.py` 的实现很粗，甚至阈值表达也比较生硬，但它至少抓住了一个方向：

- 长期上市
- 近期波动不能太大
- 但价格仍在往上扩张

这对 `monthly_slow_rise` 的启发是有的：

- 不能只看月线抬升
- 还应有波动压缩和稳定趋势层

但这里更适合“借思路，重写实现”，不适合直接迁移原规则。

## 5. 只适合参考、不建议直接接入的部分

### 5.1 单条策略实现偏硬规则，不能直接当成我们的终版口径

这个仓库的很多策略实现都比较直接：

- 固定天数窗口
- 固定均线
- 固定阈值
- 单条规则命中即通过

这适合做“形态原型”和“附加过滤器”，但不适合直接替代我们当前已经在做的多因子评分框架。

### 5.2 部分规则有明显本地经验色彩，需要重新验证

例如：

- `high_tight_flag.py` 直接要求连续两天 `>= 9.5%`
- 还要求 `istop=True`

这种条件很贴 A 股强势股经验，但：

- 会明显缩窄覆盖面
- 对不同年份行情环境适配未必稳定

所以它更适合作为“极强势标签”或“附加加分因子”，而不是基础入池条件。

### 5.3 它的系统边界偏大，不建议整套接入

仓库里包含：

- 数据抓取
- 数据库存储
- Web 展示
- 回测验证
- 自动交易

我们没必要为了借形态和筹码逻辑，把整套系统引进来。正确方式是：

- 只借策略层和筹码层实现思想
- 再映射到我们自己的数据与快照结构

## 6. 不建议引入的部分

### 6.1 不建议把它当统一研究底座

它没有 `Qlib / RD-Agent` 那种：

- 统一因子层
- 统一任务管理
- 统一实验记录
- 统一滚动评估

所以不适合拿来承接我们的研究自动化升级。

### 6.2 不建议直接沿用它的整套数据库与任务组织

它的数据库和任务方式是为自己系统设计的，不值得为了借几条策略去迁移整套表结构。

### 6.3 不建议直接沿用其“策略即结果”的判断方式

我们当前已经明确主策略要走：

- 硬门槛
- 因子拆解
- 排序
- 快照回看

所以这里更适合当“形态因子来源”，而不是“最终结果生成器”。

## 7. 映射到我们 4 条主策略

### 7.1 `trend_leader_unified`

最值得借：

- 回踩年线思路
- 平台突破思路
- 高而窄旗形标签
- 筹码集中与成本区

最适合落到：

- `stage2 / pullback` 质量字段
- `breakout_quality` 字段
- `chip_structure` 字段

### 7.2 `earnings_surprise`

直接价值不大。

可间接借的只有：

- 基本面字段组织方式
- “基本面 + 技术面 + 资金面”能放进同一张选股表的思路

但它不是 `earnings_surprise` 的主参考对象。

### 7.3 `hundred_day_high`

这是最适合吃它能力的一条策略。

最值得借：

- 海龟式新高
- 平台突破
- 放量确认
- 高旗形
- 突破前后结构过滤

### 7.4 `monthly_slow_rise`

可借：

- 低 ATR / 稳定趋势方向
- 长周期均线约束思路

但需要重写成更适合月线与周线结构的实现。

## 8. 下一步是否值得做最小实验

值得，但不建议本轮就跑整仓库。

最合适的两个最小实验是：

1. 在我们仓库里单独实现一版轻量筹码摘要层
   - 先不追求整张分布图
   - 先只产出集中度、平均成本、获利盘比例
2. 给 `hundred_day_high` 增加一版“平台突破 + 放量确认” profile
   - 与当前 profile 并行
   - 用现有 `signal_snapshot` 评估链路直接对比

## 9. 当前结论

`myhhub/stock` 对我们最值钱的不是“大而全股票系统”，而是下面 4 类可迁移能力：

1. A 股趋势突破形态的透明实现
2. 放量突破 / 缩量回踩这类质量确认逻辑
3. 筹码分布与集中度算法
4. 批量扫描后再验证的工程习惯

如果只用一句话概括：

- `myhhub/stock` 最适合服务我们当前的 `trend_leader_unified / hundred_day_high`，它提供的是“可直接落成形态与筹码增强字段”的 A 股实战实现，而不是研究底座或主信号引擎。
