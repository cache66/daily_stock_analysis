# RQAlpha 源码深挖记录
最后更新：2026-04-27

## 1. 仓库定位

`RQAlpha` 的公开定位非常明确：它是一套偏标准化、偏研究与回测口径的量化交易框架。

对我们最重要的判断是：

- 它最强的不是 A 股短线选股逻辑
- 它最强的是回测语义、账户语义、成本语义和分析输出语义
- 它最适合作为我们 `signal_snapshot` 评估链路和后续组合评估层的参考对象

本轮结论基于 2026 年 4 月官方公开仓库与文档：

- 官方 GitHub 仓库：<https://github.com/ricequant/rqalpha>
- 官方文档：<https://rqalpha.readthedocs.io/zh-cn/latest/>

## 2. 核心结构与入口

本轮优先看的真实入口包括：

- 仓库主页 README
- 官方文档中的系统架构、mod、扩展说明
- 内置 `sys_*` 模块说明
- 分析、风险、模拟撮合、交易成本相关说明

可以先把它理解成 5 层：

1. 策略运行层
   - 事件驱动策略入口
2. Mod 扩展层
   - `sys_accounts`
   - `sys_analyser`
   - `sys_risk`
   - `sys_scheduler`
   - `sys_simulation`
   - `sys_transaction_cost`
3. 数据与环境层
   - 行情
   - 日历
   - 账户
4. 回测与分析层
   - 订单
   - 成交
   - 组合
   - 风险指标
5. 扩展接口层
   - 数据源扩展
   - 事件源扩展
   - 自定义 mod

## 3. 真正的优点

### 3.1 它的“回测口径”比很多脚本项目标准得多

RQAlpha 最值得我们看的不是某个策略案例，而是它对这些事情有明确口径：

- 订单如何生成
- 成交如何撮合
- 成本如何计算
- 风险如何统计
- 结果如何分析

这恰好是我们当前本地策略体系最缺的部分。

我们现在已经有：

- 扫描
- 候选结果
- `signal_snapshot`

但还缺：

- 更标准的组合级验证
- 更清楚的成本与滑点口径
- 更统一的绩效输出

### 3.2 它的 `mod` 架构非常适合做“评估层拆分”

RQAlpha 的重要价值在于，它没有把一切塞进一个回测函数里，而是把关键能力拆成系统模块：

- 账户
- 风险
- 调度
- 分析
- 模拟撮合
- 成本

这对我们的直接提醒是：

- `signal_snapshot` 评估不应该永远只是一个脚本
- 评估层也应该逐步分模块

### 3.3 它把分析输出当成正式能力，而不是附带打印

RQAlpha 的 `analyser` 不是简单日志，而是标准结果输出的一部分。

这很重要，因为我们当前很多评估工作还偏向：

- 跑完看 JSON
- 看几个指标

但缺少更清晰的：

- 组合层指标
- 风险层指标
- 交易成本分解
- 可复用分析产物

### 3.4 它的扩展点设计值得借

官方文档明确提供：

- 自定义 `mod`
- 自定义数据源
- 自定义事件源

这意味着它不是死框架，而是一个可扩展框架。

对我们而言，这种设计最值得借的不是“接进去用”，而是它证明了：

- 数据层
- 事件层
- 回测层
- 分析层

都应该有明确接口边界。

## 4. 我们能直接用的能力

### 4.1 把它当“标准化评估层”参考对象

这是它最明确的接法。

特别适合服务我们的：

- `signal_snapshot`
- 后续组合评估
- 多策略横向比较

### 4.2 借它的成本、风险、分析三层拆分

我们后面如果要把当前评估体系升级，最适合先借这三层：

- `transaction_cost`
- `risk`
- `analyser`

因为这三层直接决定一件事：

- 现在看到的策略表现，到底是不是“可交易的表现”

### 4.3 借它的 `mod` 思想重构后续评估链路

未来完全可以把我们现有评估层逐步拆成：

- 信号转持仓口径
- 成本口径
- 风险口径
- 结果分析口径

而不是让所有逻辑继续堆在同一脚本中。

### 4.4 给 `monthly_slow_rise` 和 `earnings_surprise` 提供更好的验证方式

四条主策略里，最适合先吃评估层升级价值的其实是：

- `monthly_slow_rise`
- `earnings_surprise`

因为这两条更需要看：

- 多日持有
- 组合表现
- 成本影响
- 风险暴露

而不只是单信号短窗结果。

## 5. 只适合参考、不建议直接接入的部分

### 5.1 不建议把 RQAlpha 当主策略引擎

它的强项不是：

- A 股短线趋势识别
- 业绩超预期文本与财务混合筛选

而是评估语义。

### 5.2 不建议直接把当前 4 条主策略整体迁到 RQAlpha

这样做的改造成本太高，而且会让我们把注意力从“主策略质量”转移到“框架迁移”。

更合理的是借它的：

- 评估思想
- 口径拆分
- 输出结构

### 5.3 需要注意它的使用边界和生态依赖

RQAlpha 的价值很高，但它天然更偏完整量化框架语境。

对我们来说，更适合做基线和评估参考，而不是当前主工作流的直接依赖。

## 6. 不建议引入的部分

### 6.1 不建议为了“标准”而立即重写整套评估框架

更合理的是：

- 先对齐评估口径
- 再逐步拆层

### 6.2 不建议把事件驱动回测复杂度一次性搬进当前流程

我们现在更适合先把：

- 成本
- 风险
- 分析

三层显式化。

## 7. 映射到我们 4 条主策略

### 7.1 `trend_leader_unified`

它对这条策略的帮助主要在评估层。

最值得借：

- 成本与风险口径
- 后续组合化验证

### 7.2 `earnings_surprise`

这是很适合吃它能力的一条。

最值得借：

- 持有期评估
- 成本口径
- 风险与分析输出

### 7.3 `hundred_day_high`

主要借：

- 突破型信号在组合层的评估方式
- 交易成本与滑点口径

### 7.4 `monthly_slow_rise`

这是另一条非常适合借它的策略。

最值得借：

- 中期持有评估
- 组合与风险统计
- 更标准的回测输出

## 8. 下一步是否值得做最小实验

值得，但不建议整框架迁移。

最合适的两个最小实验是：

1. 先用它的评估维度做一版本地检查清单
   - 成本
   - 风险
   - 分析
2. 选一条主策略做“组合口径试算”
   - 优先 `monthly_slow_rise` 或 `earnings_surprise`

## 9. 当前结论

`RQAlpha` 对我们最值钱的，不是新的选股逻辑，而是下面 4 类能力：

1. 更标准的回测与账户语义
2. `mod` 化的评估层拆分
3. 成本、风险、分析输出的清晰口径
4. 后续组合评估和多策略比较的基线思路

如果只用一句话概括：

- `RQAlpha` 最适合作为我们未来“标准化评估层和组合层”的参考对象，尤其能服务 `earnings_surprise / monthly_slow_rise` 的后续验证，但不适合作为当前 4 条主策略的主引擎。
