# WonderTrader 源码深挖记录
最后更新：2026-04-27

## 1. 仓库定位

`WonderTrader` 的公开定位非常清楚：它不是一个单点选股脚本仓库，而是一套偏高性能、偏工程化、覆盖研究到执行的量化交易框架。

对我们最重要的判断是：

- 它最强的不是 A 股短线选股结论本身
- 它最强的是大规模扫描、策略引擎分层、回测与执行一体化工程能力
- 它最适合作为我们未来“全市场扫描层 + 执行层 + 高性能数据组织层”的参考对象

本轮结论基于 2026 年 4 月官方公开仓库与文档：

- 官方 GitHub 仓库：<https://github.com/wondertrader/wondertrader>
- 官方文档：<https://wtdocs.readthedocs.io/>

## 2. 核心结构与入口

本轮优先看的真实入口包括：

- 仓库主页 README
- `docs/` 与官方文档中的框架说明
- `wtpy` Python 层说明
- 引擎分类说明：`CTA / SEL / HFT / UFT`
- 数据组件与回测说明

可以先把它理解成 5 层：

1. 核心引擎层
   - `CTA` 趋势类策略
   - `SEL` 选股类策略
   - `HFT` 高频策略
   - `UFT` 超高频策略
2. Python 封装层
   - `wtpy`
   - 用 Python 编写策略、调用引擎能力
3. 数据服务层
   - 本地行情组织
   - 数据切片与高性能读取
4. 研究与回测层
   - 回测
   - 策略调试
   - 组合验证
5. 交易执行与运行层
   - 实盘
   - 风控
   - 网关与运行管理

## 3. 真正的优点

### 3.1 它对“大规模定时扫描”的工程理解很强

WonderTrader 最值得我们看的，不是高频部分，而是它把 `SEL` 单独抽成了选股引擎。

这说明它从架构上就承认一件事：

- 选股扫描
- 择时执行
- 高频撮合

不是一回事，应该分开组织。

这和我们当前最需要补的地方高度一致，因为我们现在的主问题不是“没有策略名”，而是：

- 全市场扫描如何更稳定
- 扫描和执行语义如何分层
- 扫描如何避免越来越慢、越来越乱

### 3.2 它把“高性能”放在框架层，而不是脚本技巧层

WonderTrader 的优势不是某个小优化，而是框架级设计：

- 引擎层和策略层分离
- 数据服务层和策略逻辑分离
- Python 只作为接入层，而不是全部性能负担都压在 Python

这对我们有提醒意义：

- 继续在单脚本里堆更多逻辑，收益会越来越低
- 真正能支撑 `trend_leader_unified / hundred_day_high / monthly_slow_rise` 继续扩展的，是扫描层组织方式

### 3.3 它的研究、回测、执行口径更连贯

很多开源项目只擅长：

- 回测
- 或实盘
- 或脚本扫描

WonderTrader 的价值在于，它是把这些层连起来的。

这对我们不是说“马上接实盘”，而是说明：

- 我们后面做 `signal_snapshot` 评估链路时
- 不该一直停留在“脚本筛完 -> 直接看结果”这种轻口径
- 应该逐步往更明确的回测与执行语义靠

### 3.4 它的 Python 层接法很适合做“策略壳”

`wtpy` 的存在很关键。

这说明它并不是要求所有东西都写在 C++ 里，而是：

- 性能敏感层放底层
- 策略表达层放 Python

对我们最直接的启发是：

- 我们未来如果要补高性能扫描层，不一定需要把全部业务都迁走
- 也可以保留 Python 的策略表达和文档化优势，只把重扫描、重数据组织部分往下沉

## 4. 我们能直接用的能力

### 4.1 把它当“全市场扫描架构参考对象”

这是它最值得借的一点。

特别适合服务我们的：

- `trend_leader_unified`
- `hundred_day_high`
- `monthly_slow_rise`

因为这三条都明显受全市场扫描组织方式影响。

最值得借的不是具体公式，而是：

- 如何分离扫描层与策略层
- 如何组织大批量标的扫描
- 如何让数据准备和规则评估分层

### 4.2 借它的 `SEL` 思想重构“选股引擎层”

我们当前很多逻辑还停在：

- 每条策略各自一套脚本
- 各自一套扫描入口
- 各自一套局部优化

WonderTrader 的 `SEL` 思路说明，可以显式存在一个：

- 通用市场扫描层
- 通用调度层
- 策略只声明自己的规则和字段依赖

这对我们后面统一 4 条主策略的扫描入口很重要。

### 4.3 借它的“数据服务先行”思路

WonderTrader 的很多性能收益，本质不是来自花哨策略，而是来自：

- 数据预组织
- 本地读取
- 运行时少做重复工作

这和我们最近在本地策略里遇到的瓶颈完全一致。

所以它最适合提醒我们继续往这几个方向收：

- 统一 `spot/history` 准备
- 统一扫描缓存
- 扫描前的轻前筛
- 分片扫描与调度

### 4.4 给未来组合层和执行层提供结构参考

虽然我们当前还不准备把本地策略直接接实盘，但 WonderTrader 依然有两层价值：

- 让我们知道组合层应当如何和扫描层解耦
- 让我们知道执行层应当如何和研究层分开

这对以后把 `signal_snapshot` 从单信号评估，推进到组合评估，很有参考价值。

## 5. 只适合参考、不建议直接接入的部分

### 5.1 不建议直接引入整套执行和高频栈

WonderTrader 的 `HFT / UFT` 很强，但这不是我们当前的主问题。

如果现在把注意力放到：

- 高频
- 交易网关
- 复杂执行

会明显偏题。

### 5.2 不建议把它当当前 4 条主策略的直接替代品

它给我们的是：

- 扫描和执行框架能力

不是：

- `earnings_surprise`
- `trend_leader_unified`

这类 A 股主策略答案本身。

### 5.3 不建议直接照搬底层技术选型

WonderTrader 的优势部分来自其底层实现方式，但对我们来说，现在更重要的是借它的分层方法，而不是直接复制语言和基础设施。

## 6. 不建议引入的部分

### 6.1 不建议为了性能过早做大规模底层迁移

当前阶段更合理的是：

- 先吸收它的扫描组织思路
- 再决定哪些瓶颈真的值得下沉

### 6.2 不建议把实盘执行问题前置

我们现在最缺的是：

- 扫描口径
- 因子口径
- 评估口径

不是交易接入。

## 7. 映射到我们 4 条主策略

### 7.1 `trend_leader_unified`

这是最适合借 WonderTrader 的一条。

最值得借：

- 全市场扫描组织方式
- 扫描前轻前筛
- 数据准备与规则评估分层
- 未来组合化验证入口

### 7.2 `earnings_surprise`

它对这条策略的直接帮助较弱。

主要可借：

- 扫描任务组织
- 后续评估与组合验证结构

不借其策略逻辑。

### 7.3 `hundred_day_high`

很适合借：

- 高性能扫描壳
- 分片与调度
- 扫描层与策略层解耦

### 7.4 `monthly_slow_rise`

这条也很适合借它的扫描组织能力。

最值得借：

- 全市场低频扫描结构
- 数据缓存与重复读取控制
- 与后续组合层衔接

## 8. 下一步是否值得做最小实验

值得，但应该很克制。

最合适的两个最小实验是：

1. 做一个“统一扫描壳”原型
   - 不改 4 条主策略规则
   - 只把扫描前的数据准备、分片、前筛统一
2. 对 `trend_leader_unified` 做一次 `SEL` 风格对照拆分
   - 把 universe 准备
   - history 准备
   - rule evaluation
   - result export
   明确拆开

## 9. 当前结论

`WonderTrader` 对我们最值钱的，不是具体买卖信号，而是下面 4 类能力：

1. 面向大规模选股的独立引擎思路
2. 扫描层、策略层、执行层分离
3. 高性能数据组织与本地服务思路
4. 研究、回测、执行更连贯的工程口径

如果只用一句话概括：

- `WonderTrader` 最适合成为我们未来“全市场扫描层和执行层结构”的参考对象，尤其能服务 `trend_leader_unified / hundred_day_high / monthly_slow_rise`，但不适合作为当前 4 条主策略的直接替代品。
